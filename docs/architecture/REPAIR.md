# Repair intelligence, patch handling and safe verification

Status: implemented and verified on Linux / Python 3.12. Not verified on Windows or in a real browser.

**Core rule.** A suggested fix is never called verified until the selected tests have actually run after the patch was applied and every
required criterion passed. *Applied*, *approved*, *validated* and *verified* are four different states and the API and UI keep them apart.

The proposal and the `generated` patches are deterministic; the proposal document carries `ai_assisted: false`. Since 0.19.0 a patch can also come
from Claude (`source: ai_assisted`, opt-in): it is checked by NOVA's edit gate and then follows exactly the same validation, approval, apply and
verification path as a manual patch - see `AI_ASSISTED_REPAIR.md`.

## 1. Architecture

```
failure / finding / review finding / description
        |
        v
RepairInvestigation  --evidence.assemble-->  facts | hypotheses | unknowns | next_steps
        |                                     (stored in investigation.evidence / root_cause)
        v  proposal.generate
proposal (strategy, files, side effects, tests to run, confidence, limitations)  +  autofix candidates
        |
        v  create patch (generated by autofix, or a manual unified diff)
RepairPatch  draft -> validated -> awaiting_approval -> approved -> applying -> applied -> verified | verification_failed
        |                                                                   |
        |  validate: in a temporary copy only                               |  verify: restricted pytest run   
        v                                                                   v
   working tree untouched                                         RepairVerification (criteria + baseline comparison)
```

Code lives in `backend/app/services/repair/`:

| Module | Responsibility |
|---|---|
| `patch.py` | Unified-diff parser/applier (exact matching, no fuzz), path rules, atomic write, restore, reverse diff, preview |
| `evidence.py` | Evidence assembly and root-cause ranking |
| `autofix.py` | Three deterministic rewrite rules, each verified by `ast.parse` and static re-analysis |
| `proposal.py` | Provider-independent proposal document and the single-fix lookup used for patch creation |
| `selection.py` | Test selection with a reason per target |
| `service.py` | Lifecycle, state machines, validate / submit / approve / reject / apply, recovery |
| `verify.py` | Verification start, criteria, baseline comparison, outcome |
| `errors.py` | `RepairConflict` (409) and `RepairInvalid` (422) with stable `code` values |

Reused from earlier work (no parallel abstractions): `RequestContext` and roles, `audit.record`, `make_page`, `scrub()` redaction,
`safe_join` `resolve_repository_root`, analyzers (`review.findings.analyze`), `execution.begin_existing`
`run_execution`, failures and localization, git helpers and import impact.

Data model (migration `0008`): `repair_investigations`, `repair_patches`, `repair_verifications`. A patch stores the diff text, its
SHA-256, per-file base hashes, the original text of every touched file (retained for audit and recovery), the validation report, the
approval / rejection / application metadata and a verification summary.

## 2. Evidence and ranking methodology

Statements are separated into:

* **facts** — each has a `source`, a `ref` and a `basis`: `observed` (from stored NOVA data or the files) or `stated_by_requester`
  (the requester's own description or file hints; never presented as observed);
* **hypotheses** — ranked candidate locations (file and optional symbol), always `kind: hypothesis`, `status: unverified`;
* **unknowns** — missing data that limits confidence (no coverage, no Git, no localization, ...);
* **next steps** — diagnostic actions.

Each candidate collects evidence items; its score is their sum:

| Evidence | Weight |
|---|---|
| `source_finding` (investigation opened from a finding at this location) | +5.0 |
| `localization` (score for a linked failure) | + that score |
| `static_finding_in_symbol` (open finding inside the symbol, at most 2) | +3.0 each |
| `static_finding_in_file` (elsewhere in the file, once) | +1.0 |
| `uncommitted_change` (Git reports the file changed) | +1.5 |
| `user_hint` (requester named an indexed file) | +1.0 |
| `description_mentions_file` | +1.0 |

Confidence of rank 1: `high` if score >= 6, lead over rank 2 >= 2 and at least two evidence types; `medium` if score >= 3.5; otherwise `low`.
Rank > 1 is never `high`. A best score below `NOVA_REPAIR_MIN_ROOT_CAUSE_SCORE` (default 2.0) yields **`insufficient_evidence`** — an explicit
result with unknowns and next steps, no root-cause location, and no suggested patch. The `confidence_rationale` lists the evidence used and
the data that was missing.

**Limitations.** Scores prioritise where to look; they are not probabilities and not proof. Correlation is not causation. Unindexed code is
not ranked. Runtime values are invisible. Weights are documented judgement, not calibrated.

## 3. Proposals and autofix

The proposal document has: problem statement, evidence references, suspected root cause (a hypothesis), strategy, files and symbols,
expected behavior, side effects, regression risks, tests to run (with reasons), confidence and rationale, limitations and unresolved
questions. Its `state` is `ready`, `diagnostic_only` or `insufficient_evidence`. When no safe patch exists it says so and gives diagnostic
steps; it never invents lines, names or test results.

Automatic patches exist only for rules where the rewrite is mechanical and re-checkable:

| Rule | Rewrite |
|---|---|
| `PY-COR-001` | `== None` / `!= None` -> `is None` / `is not None` |
| `PY-COR-002` | mutable default argument -> `None` plus a per-call container |
| `PY-MNT-005` | remove an unused import statement (side effects and re-exports are listed as a side effect; declined for `__init__.py`, multi-name or multi-line imports, `__future__`, star imports, and lines with `;` or comments) |

Each candidate is accepted only if the result parses, the target finding disappears on re-analysis and no new finding of the same
signature appears. Ambiguous matches are refused (`ambiguous_fix`); a changed source is refused (`stale_source`). If the investigation is
linked to a failure or finding, only fixes at the evidence locations are offered.

## 4. Patch lifecycle

Investigation: `open -> analyzed -> proposed -> patched -> applied -> verified | verification_failed`, `closed` from most states, reopen to `open`.
Patch: `draft -> validated -> awaiting_approval -> approved -> applying -> applied -> verified | verification_failed`;
`invalid` (stale/conflicting) can be re-validated; `rejected` is terminal. Any other move raises `invalid_state_transition` (409).

| Step | Endpoint | Role | Changes files? |
|---|---|---|---|
| create | `POST .../repairs/{id}/patches` | write | no |
| validate | `POST .../patches/{pid}/validate` | write | no (temporary copy, removed in a `finally`) |
| submit | `POST .../submit` | write | no |
| approve | `POST .../approve` | write | **no** (revalidates; stale -> refused) |
| reject | `POST .../reject` (reason >= 5 chars) | write | no |
| apply | `POST .../apply` with `{"confirm": true}` | write | yes, only the files in the patch |

Roles: `owner` and `maintainer` may write; `viewer` is read-only (403).

## 5. Security model

* **Paths.** Forward-slash repository-relative only. Absolute paths, `..`, `.git*` entries, NULs and suffixes outside
  `NOVA_REPAIR_ALLOWED_SUFFIXES` are rejected. Any symlink component (file or directory) is rejected, so a link cannot redirect a write
  outside the repository root. Everything is re-resolved under the repository root at apply time.
* **Content.** Binary patches and binary targets, deletes, renames and mode changes are rejected. Limits: files per patch
  (`NOVA_REPAIR_MAX_FILES`, 10), diff size (200 000 bytes), file size (500 000 bytes). Hunks must match exactly (no fuzz); overlapping or
  out-of-order hunks are refused. A file not in the investigation's relevant files (or declared `extra_files`) is an `unexpected_file`.
* **Integrity.** The diff text is hashed at creation; every later step recomputes it (`patch_tampered` on mismatch). Base file hashes are
  recorded; a changed file makes the patch `stale`/`invalid` and nothing is written.
* **Application.** Authorization and ownership checks; explicit `confirm`; status must be `approved`; the claim is an atomic
  `UPDATE ... WHERE status='approved'` plus a per-repository lock, so exactly one concurrent caller applies and the rest receive
  `already_applied`/`apply_in_progress`. Originals are captured first; writes are atomic (temp file in the same directory + `os.replace`, mode
  preserved); on any failure already-written files are restored. NOVA never commits, pushes, runs `git`-mutating commands, or executes
  arbitrary commands.
* **Validation never modifies the working tree** (`working_tree_modified: false`) and `.git` is untouched; tests assert byte-identical trees.
* **Output.** API responses and audit details exclude absolute paths and secrets (`scrub()`), and audit details never contain file content.
* **Residual risk.** There is a short window between the final staleness check and `os.replace` in which a concurrent external editor could
  race the write. It is not eliminated, only narrowed.

## 6. Verification and runner restrictions

Verification reuses the execution boundary: a restricted `pytest` subprocess (no shell, scrubbed environment, timeout, output cap,
resource limits on POSIX, refuses to run as root/administrator). **It is not a sandbox**: tests are repository code and run with the user's
privileges, network and filesystem access. Verification therefore always requires `confirm: true`, after a preview of exactly which tests
will run and why.

Selection (`selection.py`): the failing test linked to the investigation; test files that import the patched files (static import, labelled
as such); test files from discovery associations. `scope: "all"` runs every discovered test. Unknown requested ids are 422
(`unknown_test`); no discovery means a recorded **BLOCKED** verification, not an error and never PASSED.

Criteria (`pass | fail | incomplete | blocked | unavailable`): `run_completed`, `tests_executed`, `no_failures`, `no_skipped`,
`original_failure_resolved`, `no_new_failures` (vs the baseline run linked from the failure), `no_new_static_findings`. Outcome:
any `fail` -> **FAILED**; else any `blocked` -> **BLOCKED**; else any `incomplete` -> **INCOMPLETE** (timeouts, runner errors, only
pre-existing failures remaining); else **PASSED**. `PASSED` moves the patch to `verified`; `FAILED` to `verification_failed`. Evidence
(selected tests, run, criteria, comparison, bounded and scrubbed output) is kept in every case. A passing run shows that the selected
checks passed; it does not prove the change is correct.

A failure is "new" only if the baseline run covered that test and did not fail it; otherwise it is "pre-existing" or "without baseline
coverage".

## 8. API examples

All paths are under `/api/v1/repositories/{repository_id}`. Lists are paginated (`page`, `page_size`) with `status`, `severity`,
`verification_outcome`, `source_kind` and `q` filters. Errors are `{"error": {"code", "message", "details"}}`.

```bash
# create, from a recorded failure
curl -X POST $B/repairs -d '{"title":"Carts share state","failure_id":"<id>","severity":"high"}'
curl -X POST $B/repairs/$R/evidence          # facts, hypotheses, unknowns, next steps, root cause
curl -X POST $B/repairs/$R/proposal          # deterministic proposal
curl -X POST $B/repairs/$R/patches -d '{"source":"generated"}'
curl -X POST $B/repairs/$R/patches -d '{"source":"manual","diff":"--- a/pkg/x.py\n+++ b/pkg/x.py\n@@ ..."}'
curl      $B/repairs/$R/patches/$P           # diff_text + structured preview
curl -X POST $B/repairs/$R/patches/$P/validate
curl -X POST $B/repairs/$R/patches/$P/submit
curl -X POST $B/repairs/$R/patches/$P/approve
curl -X POST $B/repairs/$R/patches/$P/reject  -d '{"reason":"changes unrelated behavior"}'
curl -X POST $B/repairs/$R/patches/$P/apply   -d '{"confirm":true}'
curl      $B/repairs/$R/patches/$P/rollback   # recovery guidance + reverse diff
curl -X POST $B/repairs/$R/patches/$P/verify/preview -d '{}'          # executes: false
curl -X POST $B/repairs/$R/patches/$P/verifications  -d '{"confirm":true}'   # 202
curl      $B/repairs/$R/patches/$P/verifications
curl      $B/repairs/$R/audit
```

Stable error codes include: `insufficient_evidence`, `ambiguous_fix`, `stale_source`, `patch_conflict`, `patch_tampered`, `unexpected_file`,
`unsafe_path`, `disallowed_file_type`, `binary_patch`, `too_many_files`, `too_large`, `approval_required`, `already_approved`,
`already_applied`, `apply_in_progress`, `confirmation_required`, `patch_not_applied`, `unknown_test`, `discovery_required`,
`invalid_state_transition`.

## 9. Frontend workflow

`/repositories/:id/repairs` lists investigations (search, status / severity / verification-outcome filters, pagination) and creates new
ones (optionally linked to a recorded failure, with file hints). `/repositories/:id/repairs/:repairId` shows evidence (facts with their
source and basis, ranked hypotheses with the evidence behind each score, unknowns, diagnostic next steps, ranking method), the proposal, and
each patch with its diff (rendered as escaped text), validation, stale/invalid warnings and static re-check. Approve, reject (reason
required), apply and verify each open an inline confirmation that states what will happen; nothing is sent until confirmed. Applied,
verified, failed and blocked appear as distinct badges, with recovery instructions after apply and, for each verification, the selected
tests and reasons, criteria, baseline comparison and bounded output.

## 10. Failure handling and recovery

| Situation | Behaviour |
|---|---|
| Source file changed after patch creation/approval | `stale_source`; patch becomes `invalid`; no file written; re-validate or create a new patch |
| Write fails midway | already-written files are restored; patch returns to `approved`/`invalid` with the error recorded |
| Patch applied but wrong | `GET .../rollback` returns the reverse diff and steps (`git checkout -- <path>` or `patch -R`); files created by the patch must be deleted by hand |
| Verification FAILED | patch `verification_failed`; evidence kept; the change stays applied; create a new patch or roll back |
| Timeout / runner error | `INCOMPLETE`; never `verified` |
| No discovered tests | `BLOCKED` |
| Duplicate / concurrent apply | exactly one applies; others get 409 |

## 11. Limitations and deferred work

* Only three autofix rules; generated patches support LF files with a final newline. Everything else needs a manual diff or is diagnostic-only.
* Python / pytest verification only. No AI-generated hypotheses or patches (the proposal interface is provider-independent so one could be added).
* No automatic rollback endpoint: recovery is guidance plus a reverse diff.
* The verification runner is a restricted subprocess, not a sandbox. Not verified on Windows or in a real browser.
* A narrow race remains between the final check and the file replace (section 5).
* Background verification runs in-process (lost on restart; the verification stays `PENDING`).
* Ranking weights are not calibrated against real fix outcomes.

## 12. Worked example (disposable repository)

`backend/tests/test_repair.py::test_worked_example_end_to_end` builds a throwaway repository (`pkg/cart.py`, `pkg/other.py`,
`tests/test_cart.py`) under a pytest temp directory — never a real user project — and drives the whole flow through the HTTP API:

1. index + analysis; discovery; execute tests -> 1 failed (`test_carts_are_independent`, caused by `def add_item(item, items=[])`);
2. ingest the failure; create an investigation linked to it;
3. evidence: top hypothesis `pkg/cart.py` / `pkg.cart.add_item`, confidence high, root cause labelled an unconfirmed hypothesis;
4. proposal: `ready`, rule `PY-COR-002`, tests to run include the failing test and `tests/test_cart.py`;
5. generated patch (draft); validation leaves the tree byte-identical; apply before approval -> 409;
6. submit, approve (tree still identical), apply with `confirm` -> `pkg/cart.py` now uses `items=None`; status `applied`, **not verified**;
7. verification preview (`executes: false`), start without confirm -> 422, start with confirm -> run passes (2 passed);
8. outcome `PASSED`, criterion `original_failure_resolved: pass`; investigation and patch become `verified`;
9. the audit trail lists created, evidence, proposal, patch created / validated / submitted / approved / applied, verification started / evaluated, in order.
